# 安全事件处置记录：仓库密钥泄露（2026-10-30）

## 触发

GitHub 对本仓库发出 secret scanning 告警，指向 `tests/test_catalog_export.py#L215`
的「腾讯微信 API 应用 ID」，正文提示：泄露的信息任何具有读访问权限的人都可以查看，
建议轮换和撤销每个有效秘密。仓库为 **public**。

## 排查结论：告警指向的只是次要问题

| 泄露项 | 类型 | 位置 | 是否可轮换 | 真实风险 |
|---|---|---|---|---|
| 微信小程序 AppID `wx…` | **公开标识符**，不是凭据 | `tests/test_catalog_export.py:215`、`corpus/catalog_export.py:334`、`docs/资料库建设决策与Agent实施方案_2026-10-19.md:31,34,314` | 否（AppID 不可轮换，只有 AppSecret 可） | 低。仓库内**从未出现** AppSecret |
| bigmodel 模型 API key（`32位hex.20位`） | **真实凭据** | `benchmarks/intent/eval_strong_llm.py:54`、`benchmarks/profile_chat_latency.py:70` | **是** | **高**。已公开 1 天以上，可被用于盗刷额度 |
| DashScope API key（`sk-ws-…`） | **真实凭据** | `benchmarks/intent/eval_strong_llm.py:59` | **是** | **高**。同上 |

GitHub 的告警只提到了 AppID，但**真正高危的是两个模型 API key**——它们被写死在
`os.getenv(..., "<真实key>")` 的默认值里，仓库一公开即等于泄露。

## 根因：提交前守卫有四个洞

2026-10-29 引入的 `scripts/git-round.mjs` 声称「代码里不得有密钥」，但实际：

1. **只扫「本次变更的文件」**——已入库的历史密钥根本不在扫描范围内。
   真实 key 正是这样漏过去的：它们在更早的提交里入库，之后每次提交都不再被扫到。
2. **密钥形态覆盖不全**——只认 `tlJIT51`/`sk-`/`PRIVATE KEY`/`ghp_` 四类；
   中继 key（`32hex.20`）、`sk-ws-`、`glpat-`、`AKIA`、`AIza`、`xox`、微信 AppID 全都没覆盖。
3. **形态规则写死在脚本里**——加规则要改脚本，且**没有回归测试**，守卫失灵不会被发现。
4. **没有扫描已跟踪文件**——`git ls-files` 从未出现在扫描范围里。

## 已执行的修复

### 1. 清除凭据字面量

- `benchmarks/intent/eval_strong_llm.py`：`PROVIDERS` 去掉 `default_key`，
  改为只认环境变量（`BIGMODEL_KEY` / `DASHSCOPE_KEY`），缺失时回落到
  `benchmarks/_creds.py`（凭据唯一入口），仍缺失则**显式报错退出**，绝不静默使用写死值。
- `benchmarks/profile_chat_latency.py`：同上，去掉 `os.getenv` 默认值里的真实 key。
- AppID：测试用占位符（`"wx" + "0" * 16`，运行时拼接避免源码出现密钥形状字面量）；
  生产代码与文档改用 `SAFETYMIND_WX_APPID` 环境变量 + `<小程序AppID>` 占位符。

### 2. 守卫加固

- **密钥特征抽到 `scripts/secret-patterns.json`**（单一事实源，11 类形态）。
- **扫描核心抽到 `scripts/secret-scan.mjs`**：**无 git 依赖**，可被测试直接端到端验证。
  此前扫描逻辑与 git 操作缠在一起，受限环境下无法被测试覆盖——这正是「守卫失灵没人知道」的原因。
- **扫描范围扩到全部已跟踪文件 + 候选文件**（`git ls-files`），历史密钥不再漏网。
- 命中样例一律**打码**输出（`1871…BO（len=49）`），避免密钥再进 CI 日志。
- 规则文件缺失/非法/为空 → **退出码 6 中止**，不让守卫形同虚设。

### 3. 回归测试 `tests/test_git_guard.py`（22 项，全通过）

- 规则文件存在/非空/可编译/规则 id 唯一；
- **规则文件自身不含密钥形状字面量**；
- 11 类形态**逐一**能被对应规则命中；
- 规则之间无异常交叉命中；
- 已知测试夹具（`sk-original-…`）与普通字符串**不被误伤**；
- 守卫确实扫全部已跟踪文件、形态来自规则文件、样例已打码；
- 扫描核心与 git 解耦；
- 工作树不含任何密钥形态字面量；
- **端到端**：临时目录种入假密钥 → 扫描器退出码 3、报出规则 id、日志不含明文；
  干净目录 → 退出码 0。

### 结论：欠费**不是**这次泄露造成的

判据有四条，每条都指向自用：

1. **泄露窗口当天没有 `qwen-max` 账单行**。
   泄露的脚本 `eval_strong_llm.py` 里 dashscope provider 写死的模型是 `qwen-max`，
   而 10-30 当天 `qwen-max` 明细**行数为 0**。盗刷若发生必然有 `qwen-max` 用量。
2. **用户自己的 10-25 评测与账单严丝合缝**：
   `strong_llm_dashscope_qwen-max.json` 记录 `n=410`、0 错误、51s；
   账单 10-25 的 `qwen-max` 输入 25.651+48.768=74.419 千tokens、输出 3.157 千tokens，
   折算约 182 tokens/条 —— 与 410 条规模吻合。
3. **10-30 当天 56 行「API 调用」覆盖 33 个模型**（glm-5.3-prime、deepseek-v4 系列、
   qwen3.8 系列、kimi、图像/视频模型…），而泄露脚本**只可能调 `qwen-max`**。
   这种覆盖面是本机多模型工具链（中继网关）跑出来的，不是单一脚本被盗用能产生的。
4. **大额结构合理**：19.66 元（占 94.6%）来自 `glm-5.3-prime` 的
   9166.08 千tokens **隐式缓存命中**输入（单价 0.004 元/千tokens）+
   209.26 千tokens 未命中 + 27.72 千tokens 输出，
   且其中 17.76 元被**优惠券抵扣**。这正是本机长上下文 Agent 会话的特征
   （同前缀反复命中隐式缓存），不是随机扫描式调用的特征。

### 那欠费是什么

这份导出只有 **20.8 元**（且已用掉 17.76 元优惠券），
**远不足以造成「欠费」**。欠费应来自这个导出**未覆盖**的其它用量：
`2026-10-25` 之前的日期、或本导出未包含的产品线（训练、存储等）。
需要**更长时间跨度**的账单（10 月全月 + 9 月）才能定位。

> 换句话说：泄露是**真实存在的安全风险**（key 公开、可被他人盗用），
> 但从这份账单看，**它不是这次账单金额的来源**。
> 两个问题要分开处理：欠费要查别的账期；key 仍必须轮换。

### 唯一需要警惕的信号（量级很小，但值得查）

wan2.7-image-pro 1 张 = 0.5 元、wan2.7-image 1 张 = 0.2 元、wan2.6-t2v 2 秒、z-image-turbo 1 张）。
其中大部分被免费额度抵扣，只有 0.7 元实付。

**盗刷图像模型的典型特征是「单规格批量生成」**；这里是 9 个规格**各 1 张**、
每个都不同 —— 更像本机做功能自测时逐个规格点一遍。
但因为金额只有 0.7 元，无法从账单单独定论。
**建议**：在阿里云控制台看 **API Key 7458634 的调用日志**（含来源 IP），

无法从账单证明（账单只给 `API Key ID = 7458634`，不含 key 明文）。
